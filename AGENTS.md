# AGENTS.md

Guidance for AI coding agents working in this repo.

## Project

`buildinio` — an app builder for non-coders. Early stage: a landing page, working sign-up, log-in and accounts (with a settings pop-up), a signed-in home with a sidebar and a search of projects and their chats, and project chats where an OpenAI model builds a real Vite + React app (writing files, running npm, searching the web) and the preview shows it, plus a share link to each app on its own (private or public). Playwright regression tests cover account popup layering, the settings, tooltips, the search, project header actions, the preview, share links, how answers' Markdown looks, lists in the prompt box, the AI's questions and the AI end to end, Stop included (against a fake OpenAI). Update this file as the project grows.

## Stack

- Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4, `lucide-react` icons, `sonner` toasts.
- SQLite (`better-sqlite3`) with Drizzle ORM; Arctic for Google/GitHub OAuth; Resend for email. Node.js 22+.
- The AI: OpenAI's Responses API (`openai` SDK), OpenAI models only. Users' apps start from `templates/app` (Vite, React, TypeScript, Tailwind v4) and their commands run in Docker (Playwright's image, for screenshots), or on the host with `SANDBOX=host`.
- Font: Onest (the brand wordmark font), loaded with `next/font/google`.
- Answers are Markdown: `react-markdown` + `remark-gfm`, code colored with `lowlight` (highlight.js).

## Commands

- `npm install` — install dependencies
- `npm run dev` — dev server at http://localhost:3000
- `npm run build` — production build (also type-checks)
- `npm run lint` — ESLint
- `npm run test:e2e` — production Playwright regression tests; run `npx playwright install chromium` first, or set `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` to an installed Chromium. Uses a separate `data/playwright.db` and `data/playwright-projects`, a fake OpenAI (`tests/fake-openai.mjs`, port 3101) and `SANDBOX=host`, so no key, Docker or network is needed. Seed data with `tests/seed.ts`.
- `npm run db:generate` — after changing `lib/db/schema.ts`, writes a migration to `drizzle/`. Migrations run on server start (`instrumentation.ts`).

## Layout

- `app/` — routes (`/` and `/projects/[id]` in the `(workspace)` route group, `/signup`, `/login`, `/welcome`, `/api/auth/[provider]/callback`, `/api/projects/[id]/turn` (sends a prompt and streams the AI's answer), `/api/account/export` (the data export), `/api/avatars/[id]` (uploaded avatars), `/api/share/[id]` (the share page hears what changed), `/preview/[id]/...` (the built app), `/share/[id]` (the app on its own, at its share link)), `layout.tsx` and `globals.css` (color tokens, light/dark, animations, fades).
- `components/` — React components (`Header`, `AppShell`, `Sidebar`, `Preview`, `ProjectList`, `ProjectTile`, `ProjectHeader`, `ProjectActions`, `ShareButton`, `SharedApp`, `Watermark`, `Bone` (the shimmering skeleton blocks), `Tooltip`, `EditProjectDialog`, `SearchDialog`, `Highlight`, `ProjectChat`, `ChatMessage`, `ChatTurn`, `QuestionsCard`, `MessageText`, `UserText`, `CodeBlock`, `MessageActions`, `AccountMenu`, `SettingsDialog`, `AvatarCropper`, `Avatar`, `Hero`, `PromptBox`, `AuthFlow`, `CodeInput`, `ProviderIcons`, `Toaster`), hooks (`useKeyboardDock` keeps the prompt box and the name step above the phone keyboard; `useApplyTheme`, `useSidebarState`, `usePreviewState`, `useSwipeSheet`, `useStreamed`, `useScrollEdges`, `usePlayOnce`, `useCloseOnBackdrop`, `useProjectMenu` (a list of projects' ⋯ menu and its Edit and Delete dialogs) and `useMenuPress` (a project row's right-click and long press)) and `styles.ts` (shared class strings like `focusRing`, `circleButton`, `navItem`, `menuPanel`, `dialogPanel`, `rowOptions`).
- `lib/projects/` — projects and chats: `server.ts` (database queries), `actions.ts` (Server Actions: edit, delete, feedback, preview seen), `store.ts` (the browser's copy, and playing back the AI's answers), `ids.ts`, `changes.ts` (who's watching a project's app from its share page), `questions.ts` (the AI's questions: checking them, how the AI sees them later, the answers as a prompt), `options.ts` (project colors and icons), `search.ts` (finding projects by name or chat, and the bit of the chat to show), `types.ts` (including the streamed `TurnEvent`s).
- `lib/ai/` — the AI: `client.ts` (OpenAI settings from env), `agent.ts` (one answer: the tool loop and the build), `tools.ts`, `instructions.ts` (its system prompt, and the project's state sent with each prompt), `skills.ts`, `naming.ts`, `runs.ts` and `registry.ts` (answers in progress, on the server).
- `skills/` — well-known public skills the AI reads when a request needs one (`frontend-design` from anthropics/skills, `web-design-guidelines` from vercel-labs, `shadcn` from shadcn-ui), copied as they are with their licenses. `skills/README.md` lists where each came from and how to add one. Excluded from type-checking, lint and Tailwind's class scan.
- `lib/sandbox/` — each project's code on disk: `workspace.ts` (folders, `PROJECTS_PATH`, default `data/projects`), `files.ts` (the AI's file tools, kept inside the folder), `run.ts` (commands in Docker or on the host), `build.ts` (`npm install` when needed, then `npm run build`), `look.ts` and `screenshot.mjs` (the AI's screenshots of the built app), `snapshot.ts` (the copy of the project from before an answer, which Stop puts back; in `.snapshots` in `PROJECTS_PATH`, cleared on start).
- `templates/app/` — what every new project starts as. Excluded from type-checking, lint and Tailwind's class scan.
- `lib/lists.ts` — lists in prompts: the prompt box's list keys (`listKey`, `autoBullet`) and cutting a user's message into text and lists (`parseBlocks`).
- `lib/sidebar.ts` and `lib/preview.ts` — the sidebar's and the desktop preview's widths and cookie names, shared by the layout and the components.
- `lib/db/` — Drizzle schema and the database connection (`DATABASE_PATH`, default `data/buildinio.db`, gitignored). `drizzle/` holds the migrations. On start, `instrumentation.ts` also removes project folders whose project is gone.
- `lib/auth/` — sessions, Google/GitHub, email codes, sign-up, and `actions.ts` (the Server Actions the UI calls). `lib/email/` — the code email and sending.
- `lib/account/` — the settings: `options.ts` (themes, name and avatar limits), `server.ts` (database queries, checking a picture's type from its bytes), `actions.ts` (Server Actions: rename, theme, autocorrect, avatar upload and removal), `store.ts` (the browser's copy of the signed-in user, like the projects' store), `export.ts` (the .json download).
- `proxy.ts` — runs for every page: sends signed-in users from `/signup`, `/login` and `/welcome` to `/`, and keeps the `theme` cookie the same as the database (see Settings).
- `brand/` — logo and icons, imported directly (e.g. `import logo from "@/brand/logo.svg"`); don't copy them into `public/`. `logo-email.png` (on a white badge, for apps that force dark mode) and `logo-email-dark.png` (white, for real dark mode) are the logos rendered at 3× for emails (email apps don't show SVG).
- `public/avatars/default.svg` — the avatar for email sign-ups.

## Brand

- Logo files, colors and usage rules live in `brand/` (see `brand/README.md`). Use those files; don't redraw or recolor the logo.
- Page titles end in " - Buildinio": the root layout's `title.template` adds it, so pages set only their own part (`title: "Log in"`). The project chat swaps in the project's name (`ProjectChat`).
- UI colors are CSS variables in `app/globals.css` (`background`, `foreground`, `muted`, `surface`, `border`, `error`). Dark mode follows the user's theme setting (system, light or dark): `data-theme` on `<html>`, which the `dark:` variant in `globals.css` reads. Signed out, it follows the system.

## Signed-in home

- `/` shows the landing page (`Header` + `Hero`) when signed out, and `AppShell` with the "New" tab (greeting + prompt box) when signed in.
- `(workspace)/layout.tsx` owns the signed-in `AppShell`, keeping the sidebar and account controls mounted between New and project chats. Pages render only their content; the shell reads the active project title from client route params. Menus and the phone sidebar close on navigation. Signed-out home still renders the landing page, and project pages still check authentication.
- Desktop (`md` and up): `DesktopSidebar` with the logo (turns into the toggle on hover), New and Search tabs, Projects (newest first; an empty state of faint ghost rows and "Your apps will show up here." when there are none), and the account row at the bottom. Drag its right edge to resize (180–400px); dragging under 140px collapses it to icons. Width and collapsed state are saved in the `sidebar_width` and `sidebar_collapsed` cookies, so the page renders at that size with no jump, and remembered through `useSidebarState` when the shared layout is hidden and restored. The project list's scroll position is shared the same way (in `ProjectList`).
- Phones: New and project chats share the circular sidebar button; New keeps the avatar. Project chats have a circular preview button and a rounded title menu; long titles end in an ellipsis with a down chevron. On every screen size, the rounded project title uses an ellipsis and down chevron and opens the shared Edit and Delete actions (`ProjectActions`). The title keeps an opaque tinted background on hover and while expanded; its chevron turns upward while open. The shared project menu keeps its original compact styling and is centered under the title. The preview button keeps the same colors when pressed. `MobileSidebar` slides over the whole screen, with the avatar floating at the bottom right.
- Preview (`Preview.tsx`): the built app in a sandboxed `<iframe>` (`/preview/<id>/index.html?v=<appVersion>`), loaded only in the panel or sheet that fits the screen; "Building your app" (a skeleton shimmering in a wave) while the AI works on a project with nothing built yet, and a quiet empty state otherwise. While the sidebar or preview edge is dragged, `[data-dragging]` on the root keeps the pointer out of the frame. On desktop, the header's preview button lines up with the prompt box's right edge (the header content is `max-w-2xl` like the prompt box) and toggles `DesktopPreview`, a panel right of the chat; the Share button always sits left of it (see Share links). Drag its left edge to resize (from 320px; the chat keeps 360px); dragging under 240px hides it, and its edge stays at the side of the screen to drag it back out. Starts hidden; width and open state are saved in the `preview_width` and `preview_open` cookies and shared through `usePreviewState`, like the sidebar. On phones the button slides `MobilePreview` over the whole screen from the right: a bar with a back arrow (closes it, and gets focus when it opens), the title and the Share button on a solid background, the app under it. Swiping left on the chat pulls it in and swiping right pushes it back out, following the finger (`useSwipeSheet`; the chat and the preview are `touch-pan-y touch-pinch-zoom` so sideways moves reach it). The app's frame keeps touches to itself, so swiping it out starts on a thin strip along its left edge. It closes on navigation, Escape, or when the screen gets wider.
- Search (`SearchDialog`): the sidebar's Search tab, or Ctrl+K / ⌘K anywhere in the signed-in app (not over another dialog; other keyboard layouts go by the key's place), opens a pop-up like the settings, portaled to `<body>`; at the top on phones, clear of the keyboard. Searched in the browser, from the projects' store (`lib/projects/search.ts`), as you type. Before anything's typed it lists every project, newest first. A project matches when its name has every word typed (in any case), or one of its messages does (the newest such message; answers without their Markdown); ones found by name come first. Each result is the project's tile (its icon on its color) and name, and when found in the chat, a line of the message under the name with the words marked (`Highlight`, a `<mark>`; never in the name), from just before the first match, fading out at the end (starting with "…" when it's cut). Every row is the same height, with or without that line. Clicking a result, or Enter (the first result), opens the project and closes the search and the phone sidebar; up and down move between the box and the results. The ⋯ button sits at the right, in the middle of the row (with or without the line of chat), and works like the sidebar's (shows on hover with a mouse, right-click and long press too; `useProjectMenu`, `useMenuPress`); its menu is portaled inside the search's `<dialog>` (`ProjectMenu` goes in the nearest dialog), and Escape closes just the menu. Editing or deleting keeps the search open, unless the open project is deleted (that goes to New). It closes on navigation, Escape, the X, or a click outside.
- Account popups use a fixed portal outside the desktop sidebar, positioned from the trigger and kept within the viewport. In the phone sidebar, the portal stays in its dialog focus scope. Outside clicks, Escape, navigation, scrolling and resizing close the popup. Under the name and email, it has only Settings and Log out.
- Settings (`SettingsDialog`): a pop-up, not a page, portaled to `<body>` (so hiding the sidebar on a resize doesn't take it along). It has tabs down the left on desktop and a segmented row on phones. Profile: the avatar (pick a picture, crop it in `AvatarCropper` by dragging, the slider, the wheel, pinching or the keyboard, uploaded as a 256px WebP, or JPEG where the browser can't make WebP), the name (saved with Enter or the Save button that shows once it changed), and the email (read-only). General: the theme as three pictures of the app (system, light, dark) and the Autocorrect switch (the prompt boxes' `spellCheck` and `autoCorrect`). Data: Export (one .json file of the account, with the avatar's address rather than the picture, and each project's chat and code, without `node_modules` or `dist`) and Delete account (asks first). Everything is in the database (`users.theme`, `users.autocorrect`, the `avatars` table), not the browser. Changes show at once through `lib/account/store.ts` (name in the greeting and the account rows, theme, toasts) and are saved by its Server Actions.
- The theme is in the database. `data-theme` on `<html>` is only ever `light` or `dark` (`globals.css` has no system-theme fallback, so a chosen theme can't be overridden). `proxy.ts` copies the saved choice (`system`, `light` or `dark`) into a `theme` cookie with every page and deletes it without a valid session. The root layout's `<head>` script and `useApplyTheme` resolve `system` from the system setting, before the first paint and again when it changes (`THEME_COOKIE`, `THEME_HINT`). Only the server writes the cookie. `useApplyTheme` also puts the database's choice in the second part of the page, in case the cookie is missing or out of date, and puts the resolved theme back if something writes the choice itself onto `<html>`. Signing out follows the system again. A test checks every frame of a reload is in the saved theme, and that light stays light while the system is dark.
- Uploaded avatars are blobs in the `avatars` table (PNG, JPEG or WebP, checked from the bytes, at most 512 KB), served without sign-in at `/api/avatars/<random id>` like Google's and GitHub's pictures: cached for good, a new upload gets a new id, and the old one is deleted.
- Tooltips (`Tooltip`, wrapping the button in a `display: contents` div): a dark pill (`--tooltip` in `globals.css`), portaled to `<body>` (or the open `<dialog>`), on the side asked for unless there's no room, kept on screen, with an optional shortcut (`keys`, `"Mod"` is ⌘ or Ctrl). After 500ms of mouse hover (at once when moving on from another one), or at once on keyboard focus; never on touch, once pressed, while the button's menu is open (`aria-expanded`) or when it's swapped out (`inert`); gone on Escape, scrolling or resizing. Visual only (`aria-hidden`): the button keeps its `aria-label`. On the Share, preview, sidebar toggle and phone sidebar/preview buttons, the prompt box's add files, mic, send (↵) and Stop, and the New and Search (⌘K) tabs and the avatar only while the sidebar is collapsed (`label={null}` turns one off).
- Text that doesn't fit fades out with the `.fade-end` class (in `globals.css`) instead of ending in "…". It fades the element's last 2rem, so give it room (`flex-1`, or padding) or text that fits fades too.
- Scroll areas fade out what's scrolled past the same way: `.fade-y` + `useScrollEdges` (sidebar projects); the chat, which scrolls the page, uses background gradients under the header and above the prompt box. Every screen size uses the same gentle header fade with no solid color stop, like the fade by the prompt box.
- Hidden pages stay in the document (`cacheComponents`) and CSS animations replay when shown again, so "appear" animations use `usePlayOnce`, and only for things just made (`isNew` in the store).
- The Next.js dev badge is off (`devIndicators: false`) because every corner has a button under it.

## Projects and AI

- The AI identifies itself as the AI assistant in Buildinio when asked who it is or which AI/model it is, rather than taking a model or provider's name. This identity is set in `lib/ai/instructions.ts` and takes precedence over chat history and loaded skills.
- Projects and their chats are in the database (`projects`, `messages`); each project's code is a folder in `PROJECTS_PATH` (`data/projects/<id>`), kept until the project or the account is deleted. Deleting stops the AI if it's working on the project.
- The shared layout reads the user's projects (`listProjects`) and `AppShell` hands them to `lib/projects/store.ts`, a store outside React (`useSyncExternalStore`), so the shared sidebar and every chat see the same projects. Changes show right away and go to the server through `lib/projects/actions.ts`.
- Ids are made in the browser (`ids.ts`, 128 random bits), so a new chat opens at once. A project's id is also its preview's and share link's address. The app's files there need no sign-in (the sandboxed frame's requests send no cookies), so the id must stay long and random.
- A prompt on New creates a project and opens `/projects/[id]`; every prompt POSTs to `/api/projects/[id]/turn`, which creates the project the first time and streams the answer as NDJSON `TurnEvent`s. The answer runs on the server (`lib/ai/runs.ts`), not in the request: leaving or reloading doesn't stop or repeat it, and coming back joins in (a `snapshot` of what happened so far). An answer lost to a server restart starts again.
- The AI is set in `.env.local`: `OPENAI_API_KEY`, `OPENAI_MODEL` and optionally `OPENAI_REASONING_EFFORT` (passed on as is), plus `OPENAI_SMALL_MODEL` / `OPENAI_SMALL_REASONING_EFFORT` for naming. Without a key or model, every answer says how to set it up. API and sandbox failures end the answer with a short explanation (`problem` in `agent.ts`).
- The AI can rename the current project or change its sidebar icon and color on request with `rename_project`, `set_project_icon`, and `set_project_color`. Each shows in the tool rows and streams only the changed setting to the shared store. Values are validated against the edit dialog options; settings-only requests do not build the app. Explicit changes wait for initial naming, so it cannot overwrite them. The current name, icon and color go in the project state sent to the AI.
- The first prompt also names the project: a separate structured-output call (`naming.ts`, on the small model if set), alongside the answer; the name types itself out with its icon and color. A rename in the meantime wins.
- An answer: the AI says what it'll do, then uses its tools — web search (OpenAI's own, `search_context_size: "low"`), list/read/write/edit/delete files, run a command, load a skill — for as long as it needs, chaining requests with `previous_response_id`. It sees the chat so far (up to 50 messages, dropping the oldest 20 at a time) and the file tree. Questions get just an answer. It doesn't build the app itself: if the source files changed, the app is built after it finishes ("Building your app"); a failed build goes back to the AI to fix, twice at most.
- Cost: OpenAI caches a prompt by its start, so `INSTRUCTIONS` never changes (no file tree, no name: those go in a `developer` message just before the prompt, once per answer), every request sends `prompt_cache_key` (the project id), and the chat history's start only moves every 10 turns. The fake OpenAI in the tests answers "The instructions changed…" if that breaks. Each answer logs its requests and tokens (input, cached, output, reasoning) in the server console. Command output reaches the AI without color codes (`NO_COLOR`).
- Skills (`lib/ai/skills.ts`): the instructions list each skill in `skills/` by name and description; `load_skill` returns its `SKILL.md` (or another of its text files) and shows as "Reading up on frontend design". A `` !`command` `` line in a SKILL.md runs in the project's sandbox and its output takes its place (shadcn's `npx shadcn@latest info --json`). Read once at start, so restart after changing them.
- Apps are built from shadcn/ui parts: the AI runs `npx shadcn@latest init --base radix --preset <style> -y` in a new app (a style that suits it, so apps don't all look alike), adds the parts it needs, and sets the app's own colors, fonts and radius in `src/index.css`. The template has the `@/` → `src/` alias shadcn needs; the sandbox must reach `ui.shadcn.com`.
- `look_at_app` (`lib/sandbox/look.ts`): builds the app if it changed (the same `buildIfChanged` as the end of an answer, so it's not built twice), then `screenshot.mjs` runs where commands run (in Docker with the script and `playwright-core` mounted read-only), serves `dist/`, and takes a phone (390) and a desktop (1280) screenshot, at most two screens tall, with console errors and broken requests. Requests to this machine's network are blocked. The pictures go to the AI as `input_image`s, twice per answer at most, and stay in `dist/.look/` (not a source file, not served). In Docker it always runs in Playwright's image (`PLAYWRIGHT_IMAGE`), whatever `SANDBOX_IMAGE` is; on the host it uses `CHROMIUM_PATH`, or downloads Playwright's headless Chromium once if there's none. Still no Chromium: the tool says so and the AI carries on. `page` is lenient ("/" is the start page, "/settings" becomes "#/settings"). A failed look shows why under its X ("Not set up", "Didn't work") and logs the reason in the server console. Shows as "Looking at your app".
- Stop: while the AI answers, a red Stop button (a filled square, `bg-error`) takes the send button's place in the prompt box. It undoes everything the answer did, as if the prompt was never sent: each answer first copies the project folder without `node_modules` (`takeSnapshot`), and Stop puts it back (the source and `dist/`, with their times, so nothing rebuilds; the restored `package.json` makes the next build install again), puts back the name, icon and color the answer or the first naming set (unless changed by hand since, so a stopped first prompt leaves an unnamed "New project"), and deletes the prompt. The server aborts with `STOPPED` (`registry.ts`; deleting aborts without it) and `withdraw` in `runs.ts` streams a `withdrawn` event; the prompt goes back in the box of the tab that pressed Stop, unless something's been typed there since. Stop doesn't wait for the text to finish streaming in. A stopped command in Docker is waited for (`docker kill`) so nothing writes after the restore.
- In the chat it plays out like before: Thinking → what it says and the tools it uses (a box of rows: "Editing src/App.tsx +12 −3", a check or an X) → the steps fold away and what it said last stays as the answer. Text streams by the clock (`CHAR_MS` per letter), and the next step waits for it.
- Questions (`ask_user`, `QuestionsCard`): before a new app or a big change, the AI asks what would change the result, as many questions at once as it likes, each pick one or pick any from 2–8 short options (`parseQuestions` drops an "Other": the card always adds "Type your own…"). Calling it ends the answer: what it said becomes the message and the questions are saved on it (`messages.questions`); anything it changed first is built. The card shows under the latest answer only while nothing's being answered, one question at a time ("1 of 3", a circle for one and a square for any; number keys pick), with Back (after the first), Skip, and Next / Send; picking only moves on with Next, and Back keeps picks. The answers go as the next prompt, plain text `UserText` shows as lists (each question, then "• " + its picks, or "• Skipped: you decide", even when every one was skipped). A prompt typed instead of answering sends the questions all skipped first, as a message of its own just before it (`skipped` in the turn request), and retires the card; so does a prompt that Stop takes back (with that skipped message) (`clearQuestions`; the answers go back in the prompt box). On phones, while the keyboard is open for "Type your own…", the prompt box hides (`onKeyboard`) and the card scrolls so the field and the buttons under it sit above the keyboard (`useKeyboardDock` on the field). The AI sees the questions after its message in the history (`questionsForAI`).
- A successful build bumps `appVersion` and sets `ready` until the preview is seen: desktop opens the preview if it's hidden; phones show a small "Your app is ready" pill above the prompt box with View (opens it) and an X to dismiss.
- Share links (`ShareButton`, `app/share/[id]`): `/share/<id>` is the app on its own, full screen in the same sandboxed frame as the preview, with a `[logo] Build with Buildinio [X]` badge (`Watermark`) at the bottom right; the X hides it until the page is opened again. `projects.visibility` is `private` (the default: only the signed-in owner can open it) or `public` (anyone with the link); anyone else sees "This app isn't available", the same as for a deleted one. `/preview` follows the same rule for the app's pages (`getSharedApp` in `server.ts`), or the link's id would open a private app there; its other files load from the app's own origin, which sends no cookies, so they can't check and are only found through its pages. The page follows the app without a refresh, like the preview: a new build (`runs.ts`), turning it private or public (`setVisibility`) and deleting it (`removeProject`) call `announceChange` (`lib/projects/changes.ts`); `/api/share/<id>` re-checks what that viewer may see and sends it as server-sent events (`SharedAppState`: available with name and version, or not; the same for private and missing, and it stays connected so a waiting visitor sees the app the moment it's made public); `SharedApp` shows the unavailable or not-built notice or swaps in the new version with the enter animation, and updates the tab's title. The Share button opens a pop-up: who can open the link as a drop-down (Private / Public with icons and a check, saved at once through the store; Escape or a click elsewhere in the pop-up closes just the drop-down) and the link with the copy button whose icon turns into a check. Until the first version is built it shows "Building your app" over a little shimmering app instead (or "Nothing to share yet" if the AI isn't building), and turns into the link by itself once it's built. It sits left of the desktop preview button (always, whether the panel shows or not), and at the right of the phone preview's bar.
- Users' apps: `templates/app` (Vite + React + TypeScript + Tailwind v4 + lucide-react, `base: "./"`; no colors, fonts or components of ours: the AI picks a look per app; the prompt keeps apps to the words people need, with no hero, taglines or blurbs, and that wins over skills' hero and copy advice), built into `dist/` and served by `app/preview` with a CSP `sandbox` (its own origin, so its scripts can't reach this site; `localStorage` may not work there) and CORS for Vite's `crossorigin` scripts. Commands get 5 minutes; files 200 KB each and 5 MB in all; links out of the folder are refused. The Docker image is pulled in the background when the server starts (`prepareSandbox`), so the first build doesn't spend its time limit downloading it.
- Seconds tick while the AI works and stay next to like / dislike / copy under every answer. Like and dislike exclude each other; pressing the one that's on turns it off.
- User prompts sit on a tint of the project color; answers have no background.
- Lists in the prompt box (`PromptBox` + `lib/lists.ts`), plain text the AI reads as it is: "- " or "* " at the start of a line turns into "• " (Undo takes it back), and "1. " starts a numbered list. In a list, Enter (and Shift+Enter, the usual new-line key) starts the next item (numbered one more, the numbers after it counting on), Enter on an empty item moves it out a level or ends the list, Tab / Shift+Tab move the item (its sub-items and the selected items too) in and out a level, and Backspace just after a bullet or number takes it away. Ctrl/Cmd+Enter always sends; Enter sends on desktop only outside a list. Edits go through `execCommand("insertText")`, so Undo works; the auto-bullet waits for a microtask, or React puts the "-" back. Empty items aren't sent.
- User messages (`UserText`) keep their text as typed but show bullets (•, -, *, + and the like) and numbers ("1." or "1)") as real lists, nested by indent (disc, circle, square), an indented line under an item as part of it, and web addresses as links in a new tab. No other Markdown: what people type stays what they typed.
- Answers are Markdown (`MessageText`): headings, **bold**, *italic*, ~~strike~~, lists and task lists, quotes, rules, links (new tab), tables (bordered, scroll sideways when too wide) and code blocks (`CodeBlock`: the language over the code, a copy button, colors from highlight.js's classes, set in `globals.css` like GitHub's, light and dark). Languages: lowlight's common ones plus some more registered in `CodeBlock`; add one there. Images show as links. While an answer streams in, `settle` hides Markdown that isn't finished yet (an open `**`, a table with only its header). Wide code and tables have `data-scroll-x`, so a swipe on them scrolls instead of pulling in the preview. `tests/markdown-sample.md` has a bit of everything; the fake OpenAI answers it to a prompt with "Markdown". For the Stop tests, "slowly" also renames the project and takes 10 s over its summary, and "hold on" waits 10 s before it starts. "ask me" gets two questions, and the prompt after them "Thanks for your answers: …".
- Sidebar rows (and search results, see Search): the ⋯ button shows on hover with a mouse and always on touch screens and in the phone sidebar. The name only makes room for it while it shows. It, right-click and a long press open Edit (name, color, icon) and Delete (asks first, like deleting the account). Clicking outside either dialog cancels it (`useCloseOnBackdrop`).

## Auth

- `/signup` and `/login` do the same thing; only the headings differ. Both render `AuthFlow` (start → email code → name). The server decides: an email with an account logs in, a new one creates an account.
- Accounts are matched by email, so one account works with Google, GitHub and email codes. Only verified provider emails are accepted.
- The name step only shows for new accounts. The account is created when the name is submitted (until then it's a `pending_signups` row). Google/GitHub sign-ups land on `/welcome` with the name filled in.
- Avatar at creation: the Google/GitHub picture, or `/avatars/default.svg` for email. It's changed or removed (back to the default) in the settings, and not taken from Google/GitHub again later.
- Email codes: 6 digits, 10 minutes, one try each, at most 5 per email per hour.
- Sessions: random token in an httpOnly `session` cookie, only its SHA-256 stored, 30 days. Read the user with `getCurrentUser()` inside `<Suspense>` (it reads the request).
- Setup is in `.env.example` and the README. With no keys, email codes are printed in the server console (with a warning toast), and the Google/GitHub buttons show an error toast.
- Deleting the account (Settings, Data) deletes its projects too: their code first (`removeUserProjects`), then the rows with the user (avatars included).
- `cacheComponents` keeps visited pages and layouts alive but hidden. `AuthFlow` resets when hidden; `AccountMenu`, `AppShell` and `ProjectList` also close transient controls when the pathname changes. Logging in or out purges the browser's page cache (`revalidatePath("/", "layout")`).

## Branches

- Work on a descriptive branch: `feat/...`, `fix/...` or `docs/...` (e.g. `feat/sidebar`). Never commit to `main` or to an auto-named `claude/...` branch.
- If your session starts on a `claude/...` branch, create the descriptive branch from the latest `main` before your first commit and push it with `git push -u origin <name>`. This is the owner's explicit permission to push there instead of the assigned branch.
